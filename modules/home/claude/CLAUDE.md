# Git and GitHub keys

Each of the owner's machines (atlas: NixOS-WSL, glados: native NixOS, pbody:
Ubuntu on WSL) has its own ssh key and gpg signing subkey, both accepted by
GitHub. On any of them, git works with the normal config: ssh uses
`~/.ssh/id_ed25519` and commits are signed by that machine's subkey
automatically. Don't pass a key or `-c` overrides.

Cloud sessions have no key GitHub accepts, so they can't push or make Verified
commits. In a cloud session, don't push: hand the git work to a session on one
of the machines above, or give the owner the exact commands to run there.

# Python

On the Nix machines no Python is on PATH outside a project's devshell
(`nix develop`), and the version is whatever that project's `flake.nix`
declares: read it before assuming one.

- A bare `python3` is nixpkgs' current default, exposed as `python3` and `python`.
- A pinned package such as `python314` is that major.minor (nixpkgs never pins
  a patch version), exposed under its own name and as `python3`/`python`.

# Git workflow

## Worktrees

Name a worktree you create, and its branch, after the feature or fix only:
`worktrees/cargo-publish` on `ci/cargo-publish`. Don't add a hash or random
suffix. Create it in the `worktrees/` folder at the repository root (make the
folder when it's missing), not under `.claude/worktrees`. Base it on the project's
integration branch, which isn't always `main`, or on the worktree it builds on.

## Never commit without explicit approval

Even when a fix/change is clearly ready and the user's request implies a commit is the natural next step, **do not run `git commit` on your own**. Stop once the change is staged, propose the commit message as a header + body, and wait for the user to approve it before committing. This holds regardless of how the request was phrased — "fix this", "go ahead", etc. do not count as approval of a specific commit message; show the message first.

## Prefer amending a thematically-related recent commit over stacking a new one

Before proposing a brand-new commit, check whether the change is a continuation/fix of the same topic as a recent commit, one less than a week old or among the branch's last 10 commits (e.g. fixing a bug just introduced by an earlier commit in this same session/branch, or completing something that commit started). If so, propose **amending that commit** instead — with a new header + body reflecting the combined change — rather than adding another small commit on top. This applies even if that commit has already been pushed (amending it then requires a force-push, which itself still needs separate explicit approval per the standard force-push safety rules — surface that clearly when proposing the amend). If the change is a distinct concern, a new commit is still the right call — this is a judgment call, not a blanket rule to always squash.

## Commit/PR body: explain only the non-obvious rule

Keep the body to the one non-obvious fact that explains *why* — not a restatement of what the diff already shows, not a debugging-process narrative, not a repeat of a comment already sitting in the code. If nothing non-obvious needs explaining, a header-only commit (no body) is correct. Wrap specific technical terms (function/variable names, flags, config keys) in backticks.

For a breaking change, add a separate `BREAKING CHANGE:` footer paragraph (conventional-commit style) stating the concrete impact on the next run/deploy — don't fold it into the main body.
